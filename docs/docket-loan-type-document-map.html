2. The gap: loan type changes nothing

The form captures Loan Type (SME Term Loan · LAP · Working Capital · Top-up) and stores it — but no checklist item reads it. All four loan types get the same list.

The clearest consequence: LAP is a loan against property, and we never ask for a single property document. No sale deed, no encumbrance certificate, no valuation. A LAP file collected through Docket today would reach credit review structurally incomplete.

The good news: the engine already supports this. Conditions are generic — a rule is { field, equals } or { field, in: [...] } against any value on the case. “Ask for a sale deed only when loan type is LAP” is configuration, exactly like the partnership-deed rule that already works. No new code is required for anything in this document.

4. New checklist items this would need

Nine new items, each needing a precise description before it ships. Descriptions matter more than usual here — they are what the AI classifier reads to tell look-alike documents apart, and vague wording is how a sale deed gets filed as a rent agreement.

  1. Property title deed / sale deed
  2. Encumbrance certificate
  3. Latest property tax receipt
  4. Approved building plan / occupancy certificate (if adopted)
  5. Valuation report (if adopted — likely not borrower-supplied)
  6. Existing loan sanction letter
  7. Existing loan statement of account
  8. Debtors & creditors ageing
  9. Stock / inventory statement (if adopted)

5. How this gets implemented (no code)

Every rule above is a condition on the case's own data, in the same shape the two existing rules use:

IntentCondition
Only for LAP{ field: "loan_type", equals: "LAP" }
Only for Top-up{ field: "loan_type", equals: "Top-up" }
For term loans and working capital{ field: "loan_type", in: ["SME Term Loan", "Working Capital"] }

Delivery would be one migration in the pattern of 0015 — generated from the TypeScript config so the SQL cannot drift from it, idempotent, and applied only after your sign-off.

One behaviour note. Loan type is currently an optional field. If a case has no loan type, a rule like equals: "LAP" evaluates false and the document is simply not asked for. If these rules go live, loan type should probably become required on the create form — otherwise a case saved without it silently skips its loan-specific documents. That is a one-line config change, and worth deciding at the same time.

6. Open questions for you

1. Is the current 9-item baseline right at all? It has never been reviewed by anyone with credit-ops experience. Before adding loan-type rules, is the common core itself correct?
2. Are audited financials realistic for every applicant? A small proprietorship may not have audited statements. Should this be gated on entity type or turnover rather than asked of everyone?
3. What does a Top-up genuinely need? If the borrower already has a live facility with you, which documents can be reused from the original file, and which must be refreshed?
4. LAP property set — is my list right, and how far back? Specifically: how many years of encumbrance certificate, and do you want building plan / occupancy certificate on the borrower's list?
5. Who supplies the valuation? If your empanelled valuer does it, it should not be on the borrower's checklist at all.
6. Should GST documents become conditional on GST registration? We capture GSTIN at enquiry, so “required when the business is GST-registered” is expressible.
7. Should loan type become mandatory? See the note in section 5 — rules that depend on it are unreliable while it is optional.
8. Do different lenders need different lists? Today one workflow serves everyone. If Docket's tenants each want their own checklist, that is already supported (requirements are per-workflow) — but it changes how we roll this out.
